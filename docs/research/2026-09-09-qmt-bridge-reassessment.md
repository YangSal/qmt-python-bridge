# 大 QMT 外部 Python 桥接：目标复审与方案调研

研究日期：2026-09-09（北京时间）。状态：选型建议，尚未完成候选方案的本机验收，不是上线批准。

后续更新：本报告之后进行了[同日 P0/P1 实测](2026-09-09-p0-p1-results.md)。自动历史下载小样本成立，但本机缺少 socket/ctypes 等依赖，落地顺位调整为已验证的最小内置文件执行端；本文的候选源码分析保留，不表示候选整包已测通。

## 1. 先纠正目标

目标不是把业务搬进 QMT，也不是只读取人工准备好的缓存，而是：

> 数据采集、调度、数据库、因子和量化交易程序继续运行在用户自己的 Python 环境；大 QMT 内置 Python 只承担受控的行情与交易接口调用，通过桥接向外提供自动下载、历史读取、实时行情、账户查询、下单、撤单及交易回报。

日常历史采集不应要求用户打开“数据管理”手工下载。首次部署、登录和券商授权是运行前提，不能混同为每次取数的人工步骤。

本报告按“目标券商将关闭原生通道”这一用户给定约束设计。本轮未找到能证明公众号所述日期适用于所有券商、所有存量账户的统一官方通知；不将其日期作为已核实的全市场事实。

结论：**桥接路线符合目标；当前只读文件桥不满足目标；网上两个主要兼容桥也不能未经验证直接视为完整 MiniQMT 替代品。建议保留现有校验层，以固定版本的 xtquant_big_convert 为第一评测候选、CFQuant 为第二候选，按本机内置环境实测决定后端，不直接切换生产。**

## 3. 当前项目审查：哪些保留，哪些必须重做

### 3.1 当前独立项目仍是只读原型

本地基线提交为 `d27a54a`；工作区另有之前的启动兼容修复和文档变更。本报告不覆盖这些变更。

| 位置 | 当前行为 | 对目标的影响 |
| --- | --- | --- |
| `bigqmt_bridge/backend.py`：三个 `download_*` 方法 | 只检查 `cache_prepared`，没有提交下载请求 | 核心缺口；调用成功不能意味着已自动下载 |
| `qmt_bridge/worker.py`：操作白名单 | 只有探针、历史读取、财务读取和元数据等 | 没有快照、订阅、账户查询、下单、撤单、交易回报 |
| `qmt_bridge/strategy.py` | 2 秒定时器；每次处理一个请求 | 适合探针；不能当作已满足实时交易要求 |
| 当前文件协议 | K 线每请求最多 10 只，Tick 最多 1 只；响应上限 64 MiB | 未验证全市场吞吐、大窗口分块与背压 |
| worker 故障恢复 | 将未完成的只读请求重新放回队列 | 不能直接用于下单：上次可能已经委托，重放可能重复下单 |
| 既有设计与实施文档 | 明确以只读拆分、预先缓存为范围 | 是范围收窄，不是完整迁移完成；本次目标应作为后续设计依据 |

之前把“迁移验收阶段只读取样”逐渐当成了产品长期使用模式，导致自动下载缺失。这一方向需要纠正；不应继续要求用户手工准备缓存来证明自动采集可用。

### 3.2 已有工作仍有价值

保留外部 DataFrame/时间戳规范化、财务字段契约、五档 Tick 校验、错误上抛、样本对比、文件完整性校验和终端能力探针。文件传输可以继续用于诊断及批量历史结果，不必因为增加实时通道全部删除。

已有模拟终端记录证明：内置 Python 3.6.8 中文件桥成功往返，板块列表/成员、简版合约和单个指数成分权重有真实返回。历史行情自动下载、完整财务、账户查询及交易均未验收。`probe` 中 callable 为 true 只代表函数存在。

本机实际遇到缺少 `importlib`；原始行情读取包装 `get_market_data_ex_ori` 已被探针识别。应继续让复杂依赖留在外部，不能通过升级内置解释器或随意覆盖 pandas/numpy 来解决适配。

## 4. 网上方案综合比较

| 路线 | 是否针对“大 QMT 内置端” | 值得参考 | 对本项目的判断 |
| --- | --- | --- | --- |
| xtquant_big_convert | 是 | 较广的兼容映射、下载任务、行情推送、交易回报、传输选择及故障测试 | 第一评测候选，但有明确的历史读取语义和持久去重缺口 |
| CFQuant | 是 | 外部 xtdata/xttrader 风格、PipeHub、账户路由、Web 运维及 LITE 入口 | 第二评测候选；受限环境部署有参考价值，不能直接保证全历史/财务采集 |
| Chanlun-PRO 大 QMT 桥 | 文档明确是 | 业务系统通过 Redis 调用内置行情、账户和交易的实际集成方式 | 作为窄接口桥设计参考；不是本项目八表财务/全市场采集的已验证通用替代 |
| atompilot/qmt-bridge 等 MiniQMT HTTP 封装 | 不是消除 MiniQMT 依赖 | HTTP/WebSocket、外部客户端接入形式 | 不作为停用后的替代底座 |
| 自建文件/SQLite 桥 | 取决于服务端实现 | 少依赖、本机部署简单、历史大结果和持久任务 | 可作兜底；当前实现只读，交易语义需另做，文件本身不是问题根因 |
| 将策略全部重写进 QMT | 是 | 平台内直接调用 | 不符合“业务继续运行在自己的环境”的目标 |

前三类中的“开源兼容桥”与“Redis/ZMQ”并非互斥方案：前者是接口和运行机制，后者是传输方式，不能把它们当作完全不同的迁移层级。

### 4.1 xtquant_big_convert：优先评测，但不能原样接管

有实际可参考的历史下载、实时推送与交易实现，不只是函数名清单。重点发现：

1. **历史自动下载有内置接口路径。** RPC handler 优先找注入的全局 `download_history_data` / `down_history_data`，批量接口不存在时可逐股票调用。另有基于 Redis 的分块任务和进度状态。可复用这一方向。[下载 handler](https://github.com/litaolemo/xtquant_big_convert/blob/e9f8372176ca9f066fbc07c4887aac6f799951c2/src/bigqmt_signal_trader/redis_rpc.py#L2100)、[下载任务](https://github.com/litaolemo/xtquant_big_convert/blob/e9f8372176ca9f066fbc07c4887aac6f799951c2/src/bigqmt_signal_trader/download_jobs.py)

2. **“调用完成”仍不等于“数据完整可读”。** 同步 handler 会把内置返回 None 转为 True；任务完成计数按调用完成的股票数推进。分块时间预算在块之间检查，不能中断一个已经阻塞的 QMT 调用。必须增加外部可读性验证与超时状态，不能直接沿用成功标记作为入库依据。不同传输的下载任务支持也不等价。

3. **当前快照仍未透传 `subscribe=False`。** `_market_data_shapes` 已增加优先传递 `fill_data` 的分支，但仍有省略该参数的兼容降级分支；没有传递 `subscribe`。因此原先阻止其直接承接严格历史采集的理由并未全部消失。必须锁定本机签名，明确传参，不能自动降级到另一种语义。[行情适配源码](https://github.com/litaolemo/xtquant_big_convert/blob/e9f8372176ca9f066fbc07c4887aac6f799951c2/src/bigqmt_signal_trader/adapters/market_bigqmt.py#L506)

4. **财务和元数据更新不是全功能平替。** 财务下载尝试原生 xtdata，再尝试 ContextInfo 同名函数；指数权重下载仍直接依赖原生模块。原生服务已被关闭而内置函数未开放时，这些入口不能产生缺失的能力。[财务下载](https://github.com/litaolemo/xtquant_big_convert/blob/e9f8372176ca9f066fbc07c4887aac6f799951c2/src/bigqmt_signal_trader/adapters/market_bigqmt.py#L1196)、[指数权重下载](https://github.com/litaolemo/xtquant_big_convert/blob/e9f8372176ca9f066fbc07c4887aac6f799951c2/src/bigqmt_signal_trader/adapters/market_bigqmt.py#L1901)

5. **交易重复请求已有修复，但不是跨重启的完整保障。** #245 报告 Redis 应答丢失导致透明重发；固定版已有按账户和 request_id 去重的源码及回归测试。当前去重表是内存容器，设有 600 秒及容量边界，不能证明重启后不会重复委托。持久订单账本、未知结果对账仍由接入层保障。[已关闭问题 #245](https://github.com/litaolemo/xtquant_big_convert/issues/245)、[当前去重实现](https://github.com/litaolemo/xtquant_big_convert/blob/e9f8372176ca9f066fbc07c4887aac6f799951c2/src/bigqmt_signal_trader/redis_rpc.py#L3424)

6. **不能以传输名称推断性能或成熟度。** README 列出多种传输，但 SHM 表项明确是未实现占位；其延迟数据是维护者特定环境的测试，不能作为本机交易保证。账户查询派发线程也有近期修复；问题 #252 在本次查询时已关闭，不能再把旧问题描述直接当作当前未修复状态。[线程问题记录](https://github.com/litaolemo/xtquant_big_convert/issues/252)

7. **元数据适配仍需本机补充。** 当前 `get_sector_list` 默认不再悄悄给 13 个硬编码板块，这是改进；但该实现未采用我们已在本机验证的全局板块树遍历。因此可以保留自己的这部分适配，不必将已验证能力全部替换。[板块实现](https://github.com/litaolemo/xtquant_big_convert/blob/e9f8372176ca9f066fbc07c4887aac6f799951c2/src/bigqmt_signal_trader/adapters/market_bigqmt.py#L1230)

### 4.2 CFQuant：部署和交易接入值得参考，下载要看实际分支

1. 通用入口通过命名管道/PipeHub 接入；LITE 将桥接代码放入一个脚本。外部环境可继续使用兼容 API。通用入口本身直接导入 `importlib`，与本机已遇到的缺库问题相关；LITE 不依赖这个导入，但仍使用 ctypes、threading 等模块，不能未经探测就说它一定可运行。[通用入口](https://github.com/95ge/cfquant/blob/4d288322cf4cae45f1671d46f9bb6f64cb4b103e/qmt_scripts/CFQUANT_CTYPE_ALL_LOWLAT.py)、[LITE 入口](https://github.com/95ge/cfquant/blob/4d288322cf4cae45f1671d46f9bb6f64cb4b103e/qmt_scripts/CFQUANT_LITE.py)

2. 核心服务端会调用内置历史下载函数。所审查批量函数在没有 `download_history_data2/down_history_data2` 时抛未实现错误，没有自动改成逐股单接口。因此若当前终端只提供官方列出的单股票函数，外部批量采集适配仍需补齐。[实际下载路径](https://github.com/95ge/cfquant/blob/4d288322cf4cae45f1671d46f9bb6f64cb4b103e/cfquant/tx_trade_bridge.py#L1679)

3. 财务下载先尝试本机可调用的函数；如果没有，转为校验/预加载本地财务缓存。兼容说明对此明确提示。**有 `download_financial_data2` 入口不等于具备自动财务下载。** [实际分支](https://github.com/95ge/cfquant/blob/4d288322cf4cae45f1671d46f9bb6f64cb4b103e/cfquant/tx_trade_bridge.py#L2129)

4. 实际交易代码含 passorder、撤单、账户查询、回报转发和订单元数据落盘。但落盘元数据不能自动视作“重复请求不会再次下单”。同步查订单号还有查询等待和最后订单号兜底；多策略同账户、回报滞后时必须测试关联准确性。不能把返回 -1 一概当成安全重试的失败。[下单实现](https://github.com/95ge/cfquant/blob/4d288322cf4cae45f1671d46f9bb6f64cb4b103e/cfquant/tx_trade_bridge.py#L851)、[订单号查找](https://github.com/95ge/cfquant/blob/4d288322cf4cae45f1671d46f9bb6f64cb4b103e/cfquant/tx_trade_bridge.py#L966)

5. 高级行情/交易分离部署按项目说明需要不同 QMT 实例，不能把同一进程里的两个频道理解成完全隔离。部分 async 入口只是同步请求后调用 callback，同名方法覆盖不能代表相同时序语义。Web 控制台是运维便利，不是可靠性的证明。

结论：CFQuant 适合作为第二个受控样机，重点评估本机启动、交易回报和外部接入体验；本轮没有证据支持将其作为全数据采集的免适配替换。

## 5. 原文章中需要纠正的认识

- “只能 handlebar 驱动”不准确：官方还提供 `run_time` / `schedule_run` 和行情回调。外部策略可以继续使用自己的循环和调度；限制主要落在 QMT 内部。[系统函数](https://dict.thinktrader.net/innerApi/system_function.html)
- `1101` 不是限价常量，它是下单方式；报价类型是另一个 `prType` 参数，普通股票指定价示例使用 11。常量需要完整映射，不能机械替换几个数字。[交易函数](https://dict.thinktrader.net/innerApi/trading_function.html)
- 官方有历史行情自动下载函数，不要求所有 K 线下载都点 GUI；但财务自动下载能力不能从历史 K 线下载类推。[行情函数](https://dict.thinktrader.net/innerApi/data_function.html)
- Redis/ZMQ 只是消息传输。持久化、消费确认、事件补拉、请求去重和失联恢复必须由具体机制实现，不能从“用了消息队列”直接推出这些保证。
- 内置 Python 的文件、通信及库权限因券商配置而异。官方要求库白名单问题联系券商处理；开源工具不能赋予账户没有的授权。[官方常见问题](https://dict.thinktrader.net/innerApi/question_answer.html)

## 6. 面向实际采集任务的验收合同

原采集项目已有 `require_xtdata()` 后端选择入口，业务继续保留在外部是合理的；优先在这里接新后端，不把数据库及业务任务导入 QMT。数据源替换不等于替换清洗、入库和任务编排。

| 必需能力 | 当前业务依赖 | 验收重点 |
| --- | --- | --- |
| 自动下载 1d/1m/近端 Tick | 股票、ETF、指数 K 线与 Tick | 无预置缓存也能下载→读回；缺码、缺日期、超时必须可辨认 |
| 严格历史读取 | `get_local_data/get_market_data_ex` | `subscribe=False`、`fill_data=False` 不被丢弃；时区、量额单位、字段一致 |
| 全推与按品种订阅 | 外部量化策略新增接入 | 首帧、增量、订阅限制、断线恢复、退订、事件积压 |
| 复权事件 | 股票与 ETF 因子表 | 全区间事件完整性，不能用最新一次替代全部历史 |
| 八表财务自动更新 | 月度及历史财务采集 | 数据供应能力、公告日/报告期、多行股东及修订版本，不把本地缓存校验当下载 |
| 完整合约/板块/代码全集 | 合约快照、分类、代码集 | 不用简版合约或硬编码板块伪装完整数据；北京市场需独立核查 |
| 指数成分与权重 | 指数权重快照 | 成分全集、权重单位、时点一致，不把单个成员成功当全集通过 |
| 账户和交易生命周期 | 外部交易程序 | 资产、持仓、委托、成交、错误回报；订单关联与撤单最终状态 |

已有金融数据若来自另一供应商，字段含义、修订/公告时点和许可都需另立契约，不能静默混入原 QMT 财务表。若当前券商不提供自动财务下载，需要明确选择获授权的替代数据源或券商能力升级；这项缺口不阻止行情/交易独立验证，但会阻止宣称“全量采集迁移完成”。

当前采集任务有重试及幂等写入逻辑，可继续用于历史数据；不得把它直接复用为交易请求重试逻辑。

## 7. 推荐的职责划分与选型策略

```text
外部采集任务 / 外部交易策略（自己的 Python、依赖、数据库）
                       │
        外部稳定接口 + 数据校验 + 下载状态 + 订单账本
                       │
          可替换桥接后端（请求 / 回报 / 分块结果）
                       │
           大 QMT 内置薄执行端（按实际权限部署）
                       │
        内置行情 API、passorder/cancel、账户及交易回报
```

这是职责建议，不表示本轮已经创建这些组件。

### 7.1 建议采用的方向

1. 不再把 `cache_prepared=true` 作为自动采集前提；保留显式“仅缓存读取”模式，但它只是诊断/回测选项。
2. 先对两个固定候选做小范围验收，以 xtquant_big_convert 为第一顺位。其下载回退、事件及故障处理可参考较多，但历史读取适配必须解决后才能接管采集。
3. 保留自己的稳定接口和严格契约，不将所有业务绑定到第三方私有对象，也不靠全局遮蔽 `xtquant` 包切换后端。
4. 如果整包启动依赖或后台执行方式不适合当前券商，复用经审查的接口映射、在允许的运行机制下维持最小执行端；不是把第三方复杂运行时强塞进 QMT。
5. 当前文件协议保留用于探针和历史大结果。实时控制通道优先比较本机命名管道与获授权的本地 RPC；最终选谁由本机权限、回调时延、丢失恢复和混合负载测试决定，不凭理论毫秒数决定。
6. 首期只覆盖现有数据合同和普通股票/ETF 二级市场交易。融资融券、期货、期权、银证转账、ETF 申赎等不因上游有同名接口就自动纳入。

### 7.2 QMT 内部执行限制必须正面处理

官方使用须知明确警告策略线程内阻塞会影响其他策略，并限制多线程/多进程。候选项目使用后台线程是其实现选择，不构成所有券商均支持的保证。通信线程与调用 ContextInfo/交易接口的线程也不能混为一谈。[使用须知](https://dict.thinktrader.net/innerApi/user_attention.html)

默认采取短回调、分批处理；不在 QMT 回调内等待“下一个回调”才能完成的事件。单个底层下载如果会长时间阻塞，增加消息优先级也不能抢占它。应测量下载期间交易查询/撤单的尾延迟，必要时盘后下载或在券商允许的独立实例中隔离；不擅自启动多账户/多终端。

不同候选包含解决受限环境的加载或通信技巧。本项目只采用券商明确允许的方式，不修改终端权限检查、不规避授权控制；缺少许可时应报告限制。

### 7.3 两个不能省略的状态机制

自动下载：外部提交范围 → QMT 调用 → 外部验证能读到目标数据 → 才允许清洗落盘。任务应区分排队、运行、数据待就绪、成功、部分缺失、失败、超时/状态未知。不用 `None/True` 或两边同为空证明下载成功；停牌、休市和上市日期应作专门解释。

交易：持久保存唯一业务请求 ID 与订单备注映射，区分桥已接收、已交给 QMT、柜台已报、部分成交、已成、撤单中、已撤、废单与未知。消息重传不能产生新业务 ID；QMT 重启或 ACK 丢失后先查委托/成交再决定，不盲目重发。`passorder` 返回与委托回报是两件事，账户查询读到的本地缓存也可能滞后。[官方回报说明](https://dict.thinktrader.net/innerApi/question_answer.html)

外部账本是必要条件但不单独保证“恰好一次”：需要服务端去重、稳定订单标识和对账共同工作；无法判定时保留未知并暂停重发。行情推送可使用有限缓存/丢帧统计，交易回报则需要补拉与最终对账，不能只依赖在线推送。

安全边界：默认仅本机、账户和方法白名单、独立交易启用开关、订单限额、持久审计。文件 SHA256 只能检查损坏，不是认证。不得开放任意 Python 执行接口；远程访问若以后需要，另行设计鉴权及加密，不直接向公网暴露服务。

## 8. 建议验证顺序与停止条件

以下是后续工作的验收路线，不是已执行结果；两种候选不得同时处理同一交易请求。

| 阶段 | 做什么 | 通过条件 / 停止条件 |
| --- | --- | --- |
| P0：终端能力与入口 | 在独立模拟验证范围确认全局下载函数、ContextInfo、账户回调、可用模块和通信权限；记录启动版本 | 运行不依赖 MiniQMT/原生行情服务；不能以导入成功代替连通 |
| P1：最小自动数据闭环 | 选未缓存的已完成交易日范围；从外部下载一只股票，再读 1d/1m；随后 ETF/指数，近端 Tick 单独测 | 不需要人工下载；字段与时间正确；重复执行可复用缓存；超时/空数据明确。不得为制造冷缓存删除生产数据 |
| P2：全部数据合同 | 复权、财务八表、完整合约、板块全集、指数权重逐项测试；记录不支持项目 | 财务供应缺口先解决或明确拆分迁移，不能以空表或旧缓存验收 |
| P3：模拟交易闭环 | 先账户只读，再按明确测试标的、数量、价格和账户验证限价委托、撤单、成交/废单回报 | 必须看到对应模拟柜台记录；编辑器显示信号不等于已发出委托；当前轮不发单 |
| P4：故障与混合负载 | 模拟 ACK 丢失、断线、重启、重复请求、多策略订单关联；下载同时测账户/撤单延迟 | 不重复委托、不误认订单；未知状态可对账；尾延迟满足策略要求。部分成交等无法真实触发时明确区分模拟故障测试与终端实测 |
| P5：影子采集与切换 | 新后端先输出到隔离目录/测试目标，与有效基线比较；再分任务切换 | 不运行两套生产写入/交易；不靠强杀正在运行的采集进程切换；保留回退方案 |

自动下载验证不以 MiniQMT 正常运行作为先决条件：可以用已保存的有效历史基线或另一获授权环境的同口径样本校验；不能要求启动即将停用的服务才能证明替代方案可用。

切换不能热替换正在执行的原生调用。对于采集，等待当前任务完成，停止旧调度入口，在下一批次/新子进程中选新后端；对于交易，先对账存量委托、停止旧策略继续发单，再切新执行端，禁止双活。生产原生权限已取消后，回退只意味着暂停、保留数据/订单状态或切到仍获授权的备用通道，不能保证还能退回 MiniQMT。

## 9. 对开源项目的建议

继续使用 `qmt-python-bridge` 名称即可，与“外部 Python 连接大 QMT”目标相符。后续 README 应明确区分当前已发布只读原型和规划中的数据+交易能力，不提前宣称完整平替。

项目的差异化价值应是：受限内置环境的能力探针、数据语义保证、自动下载验收、交易安全状态与可迁移部署，而不是再罗列一份未验证的 API 清单。

若采用第三方实现，固定提交、保留 MIT 许可和版权、标注来源及本地修改；不复制券商专有程序、不发布账户/凭据或真实业务样本。智能体 skill 后续也应同步新目标，尤其禁止将手动缓存确认当下载成功、禁止把未知委托重试成第二笔订单。本轮只形成复审报告，尚未修改原 README、实现计划或 skill 的功能承诺。

## 10. 最终判断

**路线可行，当前交付不足，候选开源桥可借鉴但未达到免验收替换。**

接下来最有价值的工作是“无 MiniQMT 依赖的自动历史下载闭环 + 模拟账户交易生命周期”两条独立验证。先决定哪个后端在这台受限终端上成立，再据此重写实施计划；不继续围绕人工下载缓存完善一个偏离目标的产品。
