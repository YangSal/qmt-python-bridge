## 推荐方案与备选

推荐在既有 AutomaticBackend 上增加磁盘采集层，历史采集与实时能力验证分阶段推进。
历史复用已有的下载请求身份、unknown 对账、缓存校验与有界等待；实时先完成既定
M1b 内存通道门禁，再接只读快照与订阅。无需实现交易或账户查询来完成本次采集任务。

## 历史采集

- 独立显式配置：代码列表、周期、交易日列表、输出目录、等待预算。
- 第一批建议：000001.SZ、510300.SH、000300.SH；1d/1m/5m；最近五个已结束
  交易日。具体日期必须来自确认的交易日历，不用工作日推断节假日。
- 每个代码、周期、日期单元独立执行下载/缓存校验，再读取并校验原始 UTC 毫秒、
  字段、行数、日期范围、价格与量额。保留不复权口径及原始单位。
- 默认 gzip JSON Lines，按 history/<period>/<code>/<YYYYMMDD>.jsonl.gz 分区。
  每次运行保存独立清单：范围、版本、文件摘要、行数、请求/任务 ID、错误及状态。
- 临时文件写完、flush/fsync 后原子替换；只有数据文件和清单完整才算保存成功。
  同一输出目录单写者锁，重跑验证已有文件摘要和范围，不以存在文件作为成功依据。
- 下载前持久保存任务身份；中断后使用原 ID 对账。unknown 不换 ID 重发。
- 区分缓存命中、调用下载接口、下载后读回及本地归档。缓存命中不作为真实下载证据。
- 失败、缺字段、空结果或合法无成交待分类分别记录，不能当作全部成功。

## 实时验证与待确认边界

现行 2026-09-11 规格禁止实时行情正文落盘；本次“先存在硬盘”可能修改这个要求。
用户已澄清：本次是外部使用者获取数据后写硬盘测试，对应以下方案 1 的业务边界。
方案 2 保留作边界比较，不是当前用户需求。

1. 历史与实时都归档：实时桥接仍走内存，外部消费者显式开启归档；这是旧规格的
   业务归档例外，需要同步修改相关约定，不能偷偷用行情文件充当实时 IPC。
2. 仅历史归档：实时正文只留内存，只保存计数、错误、延迟等非行情测试摘要。

现有实时内存通道尚未实现。遵循已批准 M1b 候选顺序与验收合同：可靠同步的命名共享
内存优先，现有内置能力不足时验证本机命名管道。无已验收通道则保持 incomplete，
不把实时请求塞入现有历史文件桥。

M1b 使用合成消息验证双向挑战、长度/协议/会话/序号错误、至少 10,000 条逐条核对、
队列满载、对象权限、无行情调度、关闭与用户控制的断连重连。单次等待默认最多 30 秒，
一次探针最多 5 分钟，QMT 侧有界批次，不能阻塞等待外部进程。

通过后先验证一股一 ETF：完整快照、持续更新、源时间/接收时间、失联、乱序/缺口和
恢复。快照不冒充完整 Tick 流；盘后快照不作为盘中持续更新验收。
