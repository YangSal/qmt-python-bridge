# 普通 A 股 / ETF 实时行情与交易桥接设计

状态：对话中的范围与架构已获用户确认；本书面设计待用户审阅。
基线：`3f1e93d`。本文件是拟实施合同，不表示以下能力已经实现或通过验收。

## 1. 目标及本轮边界

外部量化程序、依赖、计算和数据库仍运行在用户自己的 Python 环境；同一台 Windows
电脑上的大 QMT 内置 Python 只执行受控的数据与交易调用。不得依赖 MiniQMT 原生服务，
不得将策略全部搬进内置解释器，不修改券商权限检查或补入未经许可的二进制模块。

用户已确认：

- 首个交易版本面向普通 A 股和 ETF 二级市场买卖，不含信用交易、可转债、期货、期权、
  ETF 申赎、新股申购、资金划转或跨机器接入。
- 交易依赖的实时行情只走内存，不写独立 IPC 行情文件，不使用内存盘/文件映射文件
  假装实现无文件通信。历史数据缓存与订单审计允许持久保存。
- QMT 界面操作由用户完成，开发者提供准确入口、配置步骤和预期日志；本机命令、Python
  程序、代码和测试由开发者执行。需要用户操作时明确暂停，不自动点击、停止策略或重启客户端。
- 模拟账户先验收。实际模拟订单的账户、标的、方向、数量、价格需在测试前确认；本设计的
  批准不是任意下单许可，也不是实盘启用许可。
- 交付源码、README、接口说明、验收记录和智能体 Skill；通过相应验收后更新开源仓库。
  不再制作安装包，提交说明不含助手产品名称，不公开账户、配置、原始行情或券商程序。

历史采集的完整迁移仍是项目目标，但与本设计新增的实时/交易子系统分别验收。本轮不会
把已有小样本 K 线通过扩大解释为 Tick、财务、全市场采集或生产切换完成。

## 2. 现状与必须先回答的问题

当前 `strategy_auto.py` 的正式入口已完成三证券×三周期单日读回，其中三组 5 分钟
实际触发下载，另外六组命中缓存。它没有账户、订单、撤单、回报或实时订阅接口。
已有文件 worker 每秒轮询一次，不能作为“共享内存低延迟交易”交付。

此前内置 Python 3.6.8 探测中，socket、ctypes、importlib 等模块不可导入；mmap、
跨进程同步、无行情时的调度能力尚未验证。函数名存在也不证明调用和回报有效。
因此先做独立能力验证，不能预先把共享内存或命名管道写成已可部署功能。

历史证据见 [正式入口首次实测](../../research/2026-09-11-auto-worker-live.md) 和
[方案复审](../../research/2026-09-09-qmt-bridge-reassessment.md)。其中第三方项目与接口
结论是当时快照；实现具体映射前需复核官方内置接口文档及本机返回结构，不照抄原生常量。

## 3. 架构与传输决策

分为三个独立职责，禁止共享一个无限增长的请求队列：

| 部分 | 内容 | 存储/通信规则 |
|---|---|---|
| 历史数据 | 下载、补历史、缓存读回、任务报告 | 保留已验证文件通道和 QMT 本地历史缓存 |
| 实时行情 | 指定证券最新快照、订阅增量、连接健康 | 仅内存通信及外部进程内缓存，不生成行情中转文件 |
| 交易控制 | 查询、发单、撤单、回报、请求对账 | 命令/在线回报走通过验收的内存通道；订单及去重账本持久化 |

候选顺序：

1. **命名共享内存，首选验证。** 使用无普通文件后端的 Windows 命名映射。只有实际导入、
   双向交换、跨进程同步、权限和故障测试均通过才采用。仅导入 mmap 或读写几字节不算通过。
2. **本机命名管道，备选。** 若共享内存不成立，验证券商允许的现有管道能力；需要有界、
   非阻塞的 QMT 侧处理方式，不能在策略回调里一直等待客户端。管道与共享内存实现不同，
   测试报告必须写清最终采用哪一种。
3. **文件模式不作为实时/交易降级方案。** 两个候选均不成立时，停止该子系统的部署并报告
   缺失能力，保留历史采集工作；不偷偷使用原文件桥，也不自动安装模块或修改终端权限。

外部只维护一个交易协调进程，承接多个策略标识；首期每个桥接实例绑定一个明确的股票账户。
不同策略不能各自直接争抢同一 QMT 执行端。多账户路由、多实例部署另行设计，不在首期自动启用。

### 3.1 通道共同合同

- 版本协商包含应用协议、消息类型、实例随机标识、会话标识和能力清单；版本不匹配拒绝工作。
- 命令带唯一业务 request ID、账户别名、策略标识、规范化参数摘要和失效时间；同 ID
  不同参数拒绝。网络/通信重试不生成新业务 ID。
- 消息长度、队列容量、证券数量和等待时间均有上限。命令满载明确拒绝；不会默默覆盖订单。
- 行情允许合并同证券旧快照，但必须携带序号、源时间、接收时间以及缺口/覆盖统计；不能
  将合并快照伪装成逐笔成交或完整 Tick 流。
- 交易回报不能使用行情的“覆盖旧值”策略。积压或检测到缺口时停止新订单并通过委托/成交
  查询补齐；无法确认一致性时保留未知状态。
- 同步必须有已验证的跨进程原语；不把 GIL、普通 Python 字典、整数写入或校验和当作
  跨进程原子性保证。不能可靠实现同步时，共享内存候选判为不支持。
- 实例启动、客户端断开及资源复用必须验证会话身份，防止旧消息在新实例中执行。未知版本、
  超长、截断、损坏、过期消息在调用券商接口前拒绝。
- 只允许明确受信任的本机身份接入。需验证所用内核对象权限和跨用户隔离；随机名字和 SHA256
  不是身份认证。同一 Windows 用户下的恶意进程不属于本项目可隔离的安全边界。
- 单纯 IPC 不落普通文件不等于操作系统绝不换页，本项目不承诺禁用 Windows 分页文件。

## 4. 首个实施单元：内存能力探针

这是后续交易工作的入口门禁，单独实施和验收；探针不查询资金、不订阅真实行情、不下单。
使用独立、版本化的 QMT 策略和有限大小的合成测试消息，不更改已运行的 `BRIDGE_AUTO_V1`。

探针依次执行以下流程，任何不支持项都形成结构化结果并正常退出，不留下无限等待：

1. 记录内置 Python 版本、必要模块导入结果、可用通信/同步能力，以及 QMT 定时与行情
   回调入口的存在性。仅检查交易函数是否存在，不调用它们。
2. 外部与内置端交换挑战值，确认不是进程内假通信；验证正反方向、边界长度、超长拒绝、
   协议不符、连接身份不符和重复序号检测。
3. 至少 10,000 条合成消息逐条核对序号与摘要，正常往返不得出现不一致，故障注入必须
   被检测且不得交付为有效消息；队列满载有明确结果。
   消息使用有界批次，不一次阻塞 QMT 完成整个压力测试。
4. 验证无行情输入时仍能处理控制请求；测量空闲及有负载时的轮询/回调调度间隔和往返延迟。
   不在未经确认的后台线程调用 QMT API，不用线程存在性替代线程安全证据。
5. 在用户允许停止/重启**探针策略**的窗口验证断开、未完成消息、重新连接和旧会话拒绝；
   不为测试自动重启 QMT 客户端或终止其他策略。
6. 关闭测试后释放本次拥有的内核对象；不扫描或清理其他实例资源。只保存能力与合成测试
   摘要，允许这些非行情诊断报告写入被忽略的 evidence 目录。

每次外部等待有界，单次诊断默认最多 30 秒，完整一次探针最多 5 分钟；超时立即报告具体
阶段与最后已确认状态。若 QMT 底层调用无法取消，不声称外部超时已经终止内部执行。

验收输出为 `shared_memory_verified`、`named_pipe_verified`、`unsupported` 或 `incomplete`，
附各项事实、错误、样本数、p50/p95/p99/max 和调度间隔。缺少用户重启配合、测试未跑完或
结果不确定记为 incomplete，不将其误记为能力不支持。只有全部必需项通过的前两者可进入
对应通道实现。
此处延迟是实测值，不预先承诺毫秒级；如果实际只支持秒级调度，必须明确说明并由用户确认
是否符合策略需要，不能仅因共享内存交换很快就上调为低延迟交易可用。

## 5. 实时行情子系统合同

外部接口覆盖最新快照、指定证券订阅、退订、订阅状态和健康状态。接口命名可借鉴 xtdata，
但公开能力清单明确字段、时间与回调语义；不通过全局替换 `xtquant` 包冒充全接口兼容。

- 起步验证一只普通股票和一只 ETF 的真实快照及持续更新，随后测试多证券与多外部策略。
- 先验证指定证券订阅，再验证全推路径；全推只有本机实际支持且数量/负载测试通过才开放。
- 每条行情包含证券代码、源时间、源序号（有则保留）、本桥序号、接收时间和来源模式。
  时间保留 UTC 基准并显式转换北京时间，不使用本机显示时区判断交易日。
- 原始五档缺失、合法空档及未知字段必须区分；不得补零伪造成有效盘口。价格/量额单位、
  数据类型及特殊值按内置接口实测合同记录，不能照搬历史 K 线结构。
- 快照与增量不混淆。外部缓存只有在完整首帧后才可供策略使用；断线、序列缺口、乱序、
  重连后标记失效并重新取得完整快照，不能保留旧缓存为“最新”。
- 交易启用配置必须明确行情最大年龄、桥接心跳失效时间和实际订阅容量；未配置或未验证
  则不允许发单。安静市场、午间休市和断线分别展示，不能只依据价格不变判断断线。
- 行情正文不进入日志、诊断文件、订单审计或崩溃转储功能。可以保存订阅配置、错误码、
  消息计数、时延统计及用于订单审计的报价序号/时间，不复制实时盘口正文。

## 6. 交易外部接口及对象

新增独立交易客户端，不改变历史 `AutomaticBackend` 的默认只读权限。接口合同先明确
“受理、已提交、柜台订单、最终状态”的区别，再提供有限的 xttrader 风格适配层。

| 能力 | 必须提供的结果 |
|---|---|
| 连接、健康、能力查询 | 版本、会话、绑定账户别名、就绪/失联/对账状态；不把导入成功当连接成功 |
| 资产、持仓查询 | 币种/金额单位、可用与冻结字段、查询时间；缺字段不静默补成零 |
| 当日委托、成交查询 | 全集或明确分页结果、原始柜台标识与本地业务 ID 映射、字段校验错误 |
| 普通买入、卖出 | 首期先验收限价；返回 request ID 和当前状态，不伪造已存在的柜台订单号 |
| 撤单 | 仅允许指定账户内身份已核实的订单；“撤单请求返回”不等于最终已撤 |
| 订单/成交/错误回调 | 可关联的事件、序号、原始状态、规范化状态和补拉标识 |
| 请求状态及恢复 | 按同一 request ID 查询、对账和人工处置记录，不提供盲目重新下单按钮 |
| 紧急停单 | 立即拒绝新订单，保留能力仍可用时的查询及撤单；不承诺自动撤掉全部订单 |

首个闭环使用限价买卖。市价、最新价等其他报价类型在独立映射和终端测试通过前明确拒绝，
不降级为另一报价类型。不将“普通 A 股/ETF”宣传成所有报价类型、所有交易所板块均已验收。
沪、深、北市场及不同板块的最小申报量、增量、零股卖出、价格精度、价格限制分别处理，
不能把“全部买入 100 股、价格两位小数”写成通用规则；无法获得有效规则或权限时拒绝发单。
卖出可用数量以该账户查询结果为依据，不把总持仓当可卖，也不对所有 ETF 硬编码同一回转规则。

具体 `passorder`、`cancel`、查询及回调字段映射必须在编码前对照官方内置 API 文档、
本机能力和模拟返回样本确认。原生 xtquant 常量仅作为外部兼容目标，不直接传给内置接口。

## 7. 订单账本、去重与恢复

外部协调进程维护持久订单账本，内置执行端在券商调用前保存持久去重/执行意图记录。
初期各账本单写者，不要求内置端具有 SQLite；采用受控本地目录的有界、原子替换记录并
检查落盘错误。事件体和状态保存格式需版本化。账户标识、订单和成交记录不进入 Git。

订单进程分为两层，不能用一个“成功”覆盖全部含义：

- **请求层**：已持久接收 → 本地拒绝或提交意图已持久化 → 已调用 / 调用结果未知。
- **柜台层**：未关联 → 已报 → 部分成交 → 已成；撤单分支区分撤单请求、部撤/已撤；
  拒绝与未知状态单独保留。保留原始柜台状态，不把未知枚举猜成成功。

关键不变量：

1. 同账户、同 request ID、同参数最多进入一次券商下单调用；不同参数同 ID 拒绝。
   该保证依赖完整持久记录与排他所有权，不宣称券商端端到端“恰好一次”。
2. 调用前持久保存失败则不调用；调用后保存失败则记录/呈现未知，阻止新订单并对账，
   不把异常统一当“未下单”。
3. ACK 丢失、超时和重启均查原 ID；提交意图存在但无终态时禁止自动重发。即便当次委托
   查询暂时为空，也不能据此证明订单未提交。
4. 关联使用经过实测的订单备注/客户端标识和账户、策略、日期等组合。禁止靠“最后一笔
   订单”猜测归属；备注被截断、重复匹配或缺失时保持未关联并要求对账。
5. 撤单有独立 request ID，记录目标订单稳定身份。与成交竞争时以柜台最终状态和累计
   成交量对账；取消请求成功不承诺原单零成交。
6. 回报重复、乱序与查询重叠不能重复计成交；成交唯一键必须包括账户和交易日，并保留
   柜台成交标识。未知标识规则在本机确认前不得启用自动交易。
7. 重启后清空新单就绪状态，先核对未终结委托/成交和持仓；无法对账则继续只读。
   未终结订单记录不按短 TTL 清除，清理不在活跃策略运行时自动执行。

## 8. 交易门禁与历史互斥

默认交易关闭。启用必须同时满足账户确认、证券与方法白名单、行情健康、资产/持仓查询
有效、未完成订单已对账、有效品种规则和本地执行所有权。
金额、数量、累计委托额度、委托频率、未完成委托数量等上限必须显式配置；缺失即禁用，
不提供宽松的实盘默认额度。外部与内置两侧检查关键限制，不能只相信外部策略自律。

新单被停用或行情过期时，不因同一新单门禁阻止身份明确的撤单请求；通信或券商接口本身
不可用时明确报告撤单能力不可用，不制造“撤单成功”。紧急停单不等于平仓。

在同一 QMT 进程中，首期交易就绪与历史下载必须互斥。实现需提供可验证的模式所有权，
历史 worker 在调用底层下载前检查；交易端须确认没有在途下载后才可就绪。旧版历史入口
不具备该门禁时，必须由用户停止旧策略并加载通过验证的入口，不能仅靠两个目录隔离。
交易模式下拒绝新历史下载；退出交易模式并完成在途请求处理后才能恢复历史任务。
既有 QMT 调用不能被抢占，消息优先级不能消除这个限制。

## 9. 实施划分与验收门禁

项目分四个实施单元，避免一次未验证的传输选择牵连全部交易功能：

| 阶段 | 交付 | 进入下一阶段的条件 |
|---|---|---|
| M1 内存能力探针 | 独立内置入口、外部探针、合成往返及权限/同步/调度报告 | 满足第 4 节；选定可用通道，若有性能限制先告知用户 |
| M2 正式内存行情与只读交易 | 有界传输、快照/订阅/退订、健康状态、账户及交易查询 | 正确首帧/增量/失效标记；数据不写 IPC 文件；查询对象与模拟端一致 |
| M3 订单生命周期 | 限价买卖、撤单、回报、持久去重、门禁及对账 | 离线故障测试通过，用户确认参数的模拟柜台闭环通过 |
| M4 稳定性与交付 | 断线重启、重复请求、混合负载、迁移说明和 Skill | 无重复/误关联委托；未知状态明确；公布支持范围及性能证据 |

每个阶段先写对应的实施计划，再执行测试驱动开发和代码复核。首先只安排 M1；其结果决定
M2 使用哪一种已批准候选。候选以外的架构、依赖安装或权限变化需要另行确认。
未完成阶段持续标为未完成，不因上阶段通过就提前在 README 宣传完整交易能力。

离线测试至少覆盖：参数/品种拒绝、同 ID 冲突、消息破损与会话错配、队列溢出、陈旧行情、

竞争、恢复对账、历史交易互斥。用可控注入测试未知状态，不发真实重复订单制造事故。

真实模拟验收记录下单前查询、明确参数、柜台委托/成交标识及最后状态；编辑器输出和函数
返回值不能代替柜台证据。买卖、撤单、回报均需有证据；无法真实触发的异常分支单列为
“仅离线覆盖”，不伪装为终端测试通过。不为完成验收转用实盘或扩大测试金额。

性能证据分别报告内存纯通信、QMT 调度、行情源到外部、订单到柜台回报的 p50/p95/p99/max，
不可相互替代。报告样本数、持续时间、证券数和并发负载，不能用单次最快值宣传性能。
至少完成一个交易日会话的模拟稳定性观测后再称为持续运行验收通过；跨日及重启单列测试。
